- [ ] (from: backend-dev) (to: @frontend-dev) **BaseLayout cannot express "this page should declare no canonical" — and the 404 page is a page that should not.** Follow-up to QA's N2, which I have fixed on my side; this is the principled half and it lives in your file, so it is your call and it is not urgent. src/layouts/BaseLayout.astro:27 is `const canonical = new URL(canonicalPath ?? Astro.url.pathname, base)`, and lines 39 and 54 emit `<link rel="canonical">` and `og:url` unconditionally. So `canonicalPath?` being optional means "guess it for me", and there is no way for a page to suppress the tags. For every real route that is exactly right. For the error page it is not: a canonical names the preferred URL of a resource, and an error page is not a resource. At serve time this HTML is returned for *whatever unknown path the visitor requested*, with status 404 — I verified it, `curl http://localhost:4321/some-random-typo` returns the 404 body carrying `<link rel="canonical" href="http://localhost:4321/404">`. So the canonical is inaccurate for every real visitor and only accurate for the direct hit on `/404` that nobody makes. What I would suggest, if you agree: let `canonicalPath` accept `null` (or add a `noindex` prop) to mean "emit neither tag", and have the 404 page also emit `<meta name="robots" content="noindex">`. Then I would pass `canonicalPath={null}` from src/pages/404.astro and delete my workaround. Genuinely low priority — the HTTP 404 status is the authoritative de-indexing signal and it is already correct, so the tags are inert either way; the current `/404` at least resolves. Do not let it block anything. Heads-up if you do it: tests/unit/canonical-urls.test.ts:69 asserts one canonical per emitted page, so QA would need to except 404.html there too. **PARKED by @lead 2026-08-20 as a documented known limitation. @qa concurs — this is the right call, with one precondition recorded below.** My position as the quality gate, since I was asked for it plainly: backend-dev is right on the principle and @lead is right on the priority, and those are not in tension. The reason the tags are inert is not that they are unimportant but that the HTTP status outranks them — a response carrying 404 is not indexable at all, so a `rel=canonical` in its head is discarded before it is interpreted, and a `noindex` on it would be redundant with the status rather than additive. The failure mode a wrong canonical actually causes is soft-404 consolidation, and that requires the page to be served **200**. Verified it is not: `tests/server.mjs` returns 404 for `/nope-unknown-path` with the 404 body. I also checked the two things that would have escalated this past low if either were true — `/404` is **not** in `dist/sitemap-0.xml` (nothing invites a crawler to it) and nothing in the built site links to it — and neither is. So the harm path is closed twice over, and the fix costs a `src/layouts/**` change, a CONTRACTS §3 prop-signature amendment and a QA test exception for an inert tag. Parking is proportionate. **The precondition, which is the part worth not losing:** all of that rests on the host returning a real 404 status for unknown paths. That is true of `tests/server.mjs` and of most static hosts by default, but it is a per-host configuration and no deployment target has been chosen — `site` is still `http://localhost:4321` per CONTRACTS §4. Some static hosts serve the error document with **200** unless explicitly configured otherwise, and on such a host this stops being cosmetic: `/404` becomes a real, indexable page and the canonical starts actively telling crawlers to consolidate into it. **Re-open this at deploy time and confirm the host returns 404, not 200, for an unknown path.** Until then I am content to leave it.
