## 2. New coverage

Everything below is new this pass. Counts are tests, not assertions.

**`tests/unit/schema-behaviour.test.ts` (26) — the negative case, executed.**
The existing schema suite transcribes the §2 table and measures the markdown on
disk. That can only prove the *published* content is conformant; it can never
prove the schema would *stop* a bad post, because a bad post never gets
committed. So the guarantee the contract actually sells — "a post without two
real sources fails the build" — was untested by construction. This file runs the
real zod objects from `src/content.config.ts` over fixtures:

- `posts` rejects 1 source, 0 sources, and a missing `sources` key; rejects a
  missing `verifiedDate`, a non-URL source URL, out-of-range title/description,
  a category outside the enum, 0 or 6 tags, and a non-kebab tag.
- `personal` **accepts** a post with no `sources` and no `verifiedDate`, defaults
  `tags` to `[]` and `author` to `Niklas Klasen`, accepts a 20-char description
  that `posts` rejects (asserted in the same test, so the two bounds cannot have
  collapsed into one), accepts 6 tags and `originalUrl`.
- `personal` is still not a free-for-all: rejects `sources: []`, >6 tags, a
  non-kebab tag, a missing title/description/pubDate, a non-URL `originalUrl`,
  and does not carry a `category` through the parse.

`astro:content` is a virtual module that only exists inside an Astro build, so
`vitest.config.ts` aliases it (and `astro/loaders`) to stubs under
`tests/unit/stubs/`. The stub implements `defineCollection` as the identity
function it is; the zod schemas are unmodified. This is a deliberate exception to
this suite's "never import the app" rule, documented at `vitest.config.ts:3`.

**`tests/unit/no-slug-urls.test.ts` (25) — §3's second hard rule.**

## Is the `null` branch still covered? Yes — and I verified it by breaking it

**This is the thing that was most likely to be quietly lost, so it was tested by
mutation rather than by inspection.**

Until this afternoon the null branch was covered *incidentally*: every entry in
the build took it, so the `dist/` sweep and the `/about/` text check exercised it

branch any more.** Deleting the two tests without replacing them would have

New file: **`tests/component/contact-links.test.ts` (12 tests)**. It renders the

- a `null` href renders as `<span class="contact-links__pending">Email</span>`,

## What replaced the two stale tests

The sweep over `dist/` is **unchanged in strictness** and slightly widened:

- `no href="#"`, no empty href, no `javascript:` href — on every emitted HTML
  file, exactly as before;
- **new**: no `<a>` with no `href` attribute at all, and no `href="null"` /
  `href="undefined"` — the other shapes a mis-rendered unset entry could take;
- **new**: every `mailto:` anywhere in the build must be an address §7 declares,
  so an invented address cannot appear even on a page nobody thought to check.

Positive rendering, driven by the contract rather than by a literal —
`build-output.test.ts` now parses the `CONTACT_LINKS` block **out of
docs/CONTRACTS.md** and asserts, for `/about/` and for the footer (sampled on
`/`), that each entry renders on the branch its declared href implies: a live href
as `<a href="<exact address>">Label</a>`, a `null` href as pending text and
explicitly not as a link. That test needs no edit if an entry moves back to
`null` — it follows the contract in either direction.

In `site-identity.test.ts`, the replacements are:

- `CONTACT_LINKS` in `src/lib/site.ts` equals §7's list exactly — label, address
  and order;
- **the invariant that outlives both states**: every href is either a real
  `mailto:`/`https:` address or `null` — never `#`, `''`, `TODO` or a guess. This
  is what the deleted test was *for*; it now reads whatever §7 declares instead of
  hard-coding the placeholder answer;
- the `string | null` type has not been narrowed away in `src/lib/types.ts` — if
  it becomes `string`, the plain-text branch is dead code and the next unset
  contact has nowhere safe to go.
