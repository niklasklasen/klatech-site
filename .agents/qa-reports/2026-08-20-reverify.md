## New findings

### N1 — LOW (tooling). `npm run links` discards linkinator's exit code

`package.json:16`. The gate crawls correctly but cannot fail — proven above by
fault injection. Fix is to capture the status before killing the server:

```json
"links": "node tests/server.mjs & sleep 1 && linkinator http://localhost:4321/ --recurse --skip '^https?://(?!localhost:4321)'; status=$?; kill %1 2>/dev/null; exit $status"
```

Two smaller notes for whoever edits the line: `sleep 1` is a fixed-delay race
that will eventually flake on a loaded machine, and `kill %1` relies on job
control being available in npm's non-interactive `sh` (it works here, but a
`$!`-captured PID is sturdier). Owner: **@lead** (`package.json`).

### N2 — LOW. The 404 page's canonical URL is itself broken

`dist/404.html` declares both `<link rel="canonical">` and `og:url` as
`http://localhost:4321/404/`, but the build emits `dist/404.html`, not
`dist/404/index.html`. Measured against `tests/server.mjs`, which mirrors
static-host behaviour:

```
/404       -> 200
/404.html  -> 200
/404/      -> 404
```

Broken by exactly one trailing slash. Cause: `src/pages/404.astro` does not pass
`canonicalPath`, so `src/layouts/BaseLayout.astro:27` falls back to
`Astro.url.pathname`, which is `/404/` at build time. That fallback is right for
every other route — of 20 canonical/`og:url` declarations across 10 pages, these
two are the only broken ones. The 404 page is the single page emitted as a bare
`.html` rather than a directory, so it is the single page the fallback gets
wrong. A one-line `canonicalPath="/404"` fixes it; declaring no canonical at all
on an error page would also be defensible.

Severity is low deliberately: a 404 page returns HTTP 404 to every crawler, so
the canonical is inert and real-world impact is close to nil.

Worth recording is *how* this surfaced, because it is a permanent hole in the
link gate rather than a one-off. `linkinator` crawls outward from the home page,
so it only ever sees URLs something links to. Nothing links to the 404 page — a
static host serves it in response to unknown paths — so no crawl reaches it, and
anything broken in its `<head>` is invisible to the link check for ever. It
became visible only as a side effect of the N1 fault injection, when linkinator
followed my broken link, received the 404 body, and crawled *that*. The new
`tests/unit/canonical-urls.test.ts` closes the hole statically.

Owner: **@backend-dev** (`src/pages/404.astro`).

### N3 — LOW (tooling). The QA suite depends on two undeclared packages

`tests/unit/build-output.test.ts` imports `fast-xml-parser` and, with
`content-schema.test.ts`, `js-yaml`. Neither is in `package.json`. They resolve

Fix is `npm i -D js-yaml fast-xml-parser`, which is `package.json` plus an

### KL1 — Error pages declare a canonical and an `og:url`, and should not

`src/layouts/BaseLayout.astro` emits `<link rel="canonical">` and `og:url`
unconditionally, so `canonicalPath?` means "omit it and I will guess", not
"omit it and I will emit nothing". The principled answer, which backend-dev
raised and I agree with, is that an error page should declare neither, plus
`<meta name="robots" content="noindex">`: a canonical names the preferred URL of
a *resource*, and an error page is not one — it is returned for whatever unknown
path the visitor requested, so `/404` is accurate only for the direct hit nobody
makes. Expressing it needs a `src/layouts/**` change (frontend-dev), a
CONTRACTS §3 prop-signature amendment, and an exception in
`canonical-urls.test.ts:69`.

**@lead parked it. I was asked plainly whether that is the wrong call. It is
not — I concur, with one precondition.**

The reasoning, since "low impact" on its own is the kind of claim that ages
badly. The tags are inert because the *HTTP status outranks them*: a response
carrying 404 is not indexable at all, so a `rel=canonical` in its head is
discarded before it is interpreted, and a `noindex` would be redundant with the
status rather than additive. The failure mode a wrong canonical actually causes
is soft-404 consolidation, and that requires the page to be served **200**.
I verified it is not — `/nope-unknown-path` returns 404 with the 404 body. I
also checked the two facts that would have escalated this past low: `/404` is
**not** in `dist/sitemap-0.xml`, and nothing in the built site links to it. The
harm path is closed twice over, and the fix costs three agents and a contract
amendment for an inert tag. Parking is proportionate.

**The precondition is the part worth not losing.** All of the above rests on the
host returning a real 404 status for unknown paths. That is true of
`tests/server.mjs` and true of most static hosts by default, but it is per-host
configuration and **no deployment target has been chosen** — `site` is still
`http://localhost:4321`. Some static hosts serve the error document with **200**
unless explicitly configured otherwise, and on such a host this stops being
cosmetic: `/404` becomes a real, indexable page and the canonical starts
actively telling crawlers to fold the error page into it — the textbook soft-404
signal, and worse than the bug that was just fixed.

**Re-open at deploy time and confirm the host returns 404, not 200, for an
