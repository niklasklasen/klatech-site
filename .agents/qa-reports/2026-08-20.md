## Findings, ranked

### F1 — SERIOUS (new). Code-comment syntax colour fails WCAG AA, in *both* colour schemes

`astro.config.mjs` (no `markdown.shikiConfig`) → Astro's default single `github-dark` theme.
Its comment token colour `#6a737d` on the block background `#24292e` measures **3.05:1**,
below the WCAG 2 AA minimum of 4.5:1 for body text.

- axe-core `color-contrast`, impact **serious**, **6 nodes** on the post page.
- Fails identically at `prefers-color-scheme: light` **and** `dark`, and at 360px.
- Affected text is not decorative: the failing spans are the instructional comments in the
  runnable CLI samples, e.g. `# 1. The perimeter`.
- Every other Shiki token passes (5.52, 5.79, 7.06, 8.69, 11.5:1). Only comments fail.

**This is not the same defect as the already-filed dual-theme ticket, and that ticket's fix
will not close it.** Adding `themes: { light: 'github-light', dark: 'github-dark' }` repairs
the light-mode appearance, but dark mode keeps `github-dark`, whose comment colour still
measures 3.05:1. Whichever dark theme is chosen must be re-measured before the ticket closes.

Reproduce: `npm run build && npm run test:e2e -- a11y.spec.ts` → `axe: post (light)`, `axe: post (dark)`,
`axe: post page at 360px`.
Owner: **backend-dev** (`astro.config.mjs`).

### F2 — MODERATE (new). `SITE_DESCRIPTION` does not match CONTRACTS §7, and it ships

`src/lib/site.ts:3-4` declares:

> `'Field notes on Azure network security, cloud security posture, and the security of AI systems — sourced, dated, and checked.'`

CONTRACTS §7 specifies:

> `'Azure network security, cloud security, and AI security for practitioners.'`

Not cosmetic — the §7 string is what the contract froze, and the actual string is rendered in
production output in five places: `<meta name="description">`, `og:description`,
`twitter:description` and the visible lead paragraph on `/`, plus the `<description>` of the
RSS channel.

Only `@lead` can resolve this: either the contract is authoritative and `src/lib/site.ts`
changes, or the shipped string is preferred and `docs/CONTRACTS.md` §7 needs amending. Docs
are frozen, so I am not guessing which.

Reproduce: `npm test -- site-identity` → *"src/lib/site.ts exports SITE_DESCRIPTION exactly as the contract states"*.
Owner: **@lead** (decision), then backend-dev applies.

### F3 — LOW (already ticketed; verified, not re-filed). §7 duplicate site identity is latent, not live

The lead asked specifically whether the strings actually diverge in rendered output.
**They do not.** `src/components/site.ts:12` still declares `name: 'Agent Blog'` rather than
importing `SITE_TITLE`, but every rendered instance is byte-identical:

| Surface | Source | Rendered |
|---|---|---|
| Header wordmark | `SITE.name` (components) | `Agent Blog` |
| `og:site_name` | `SITE.name` (components) | `Agent Blog` |
| `<title>` suffix | `SITE.name` (components) | `Agent Blog` |
| RSS `<channel><title>` | `SITE_TITLE` (lib) | `Agent Blog` |
| `<h1>` on `/` | `SITE_TITLE` (lib) | `Agent Blog` |

So the §7 violation is real but currently **zero user-visible impact** — a duplicate waiting
to drift, exactly as §7 anticipates. Existing lead ticket stands; `tests/unit/site-identity.test.ts`
now pins it so drift fails the build rather than shipping.

Two related observations while confirming this, neither worth a ticket:

- `SITE.description` (`src/components/site.ts:14`) is **dead code** — never rendered anywhere.
  It is a third, different description string; deleting it removes the likeliest drift vector.
- `SITE.tagline` **is** rendered (site footer, and the `<link rel="alternate">` title) and has
  no counterpart in `src/lib/site.ts`. Whoever consolidates §7 needs somewhere to put it.

### F4 — LOW (already ticketed twice; verified, not re-filed). §2 amendment still unapplied

`src/content.config.ts:18` reads `z.string().url()`; CONTRACTS §2 was amended 2026-08-19 to
`z.url()`. Behaviour is correct either way (validation still rejects a non-URL). This is the
sole remaining `npm run check` hint — the only thing between the project and a fully clean run.
Pinned by `tests/unit/content-schema.test.ts`.

### F5 — LOW (new). Both table scroll-regions get the same accessible name

`src/layouts/BaseLayout.astro:86` labels every wrapped table `'Table'` when the markdown has no
`<caption>`. The post has two tables, so two `role="region"` landmarks share the accessible
name "Table".

- axe-core `landmark-unique`, impact **moderate** (non-blocking for the gate, but observed failing).
- A screen-reader user listing regions gets "Table", "Table" with nothing to tell them apart.
- Cheap fix: fall back to the nearest preceding heading, or number them.

Reproduce: `npm run test:e2e -- a11y.spec.ts` → logged under `[axe non-blocking] post`.
Owner: **frontend-dev**.

### F6 — LOW (new, tooling). `npm run links` silently scans zero links

`package.json:16` — `linkinator dist --recurse --skip '^https?://'` reports
*"Successfully scanned 0 links"* and exits 0. It is a **green light that proves nothing**:
pointing linkinator 8.0.4 at a directory path (or even at `dist/index.html`) crawls nothing.

The check itself passes once invoked correctly — against the served build it crawls 13 internal
links with 0 broken — so this is a tooling defect, not a link defect. Suggested script:

```
"links": "linkinator http://localhost:4321/ --recurse --skip '^https?://(?!localhost:4321)'"
```

run against a served `dist/` (e.g. `node tests/server.mjs`).
Owner: **@lead** (`package.json`).

## Severity ratings for the two pre-ticketed issues

**Code blocks dark in light mode → the ticket as written is LOW; the config it lives in hides a SERIOUS one.**
Taken on its own the visual mismatch is cosmetic, and I can say that with a number: the code
text measures **11.5:1** against its own background, so the block is entirely readable — it is
an aesthetic discontinuity (a dark slab on a `#fcfcfb` page), not an accessibility barrier.
Left alone it would be a fair backlog item to defer. It should nevertheless be fixed now,
because F1 lives in the same one-line config change and F1 is a genuine AA failure. Fix them
together, and re-measure the chosen **dark** theme's comment colour — the dual-theme change
alone leaves F1 open.

**Markdown tables keyboard-scrollable only with JS → LOW. The lead's rating is correct.**
Confirmed real: at 360px with JavaScript disabled, both tables overflow (409px of content in a
318px box; 551px in 318px) and carry no `tabindex`, so their clipped columns cannot be reached
by keyboard. But the blast radius is narrow:

- With JS enabled — the normal path — the BaseLayout enhancement adds `tabindex`/`role` and
  axe raises no `scrollable-region-focusable` violation. Verified.
- Without JS, mouse and touch scrolling still work; only keyboard-only *and* JS-disabled users
  are affected.
- **Code blocks are not affected at all**: Shiki emits `tabindex="0"` on `<pre>` server-side, so
  2/2 code blocks are keyboard-scrollable with JS off. The defect is tables only.

Worth noting for whoever picks it up: no CSS change can fix this, because markdown emits a bare
`<table>` with no wrapper — the only build-time fix is a rehype plugin, which lives in
`astro.config.mjs` (backend-dev's file), not frontend-dev's. That ownership split is the real
reason to leave it parked. Filing it as a note, not a ticket, matches its severity.

## What I could not test

Stated plainly, because a gate that overclaims is worse than one that fails.

- **Single-post corpus.** There is exactly one published post, so schema conformance is proven
  against one sample. Untested for lack of data: newest-first ordering on `/`, tag pages with
  more than one post, and pluralisation on `/tags/`. The draft-exclusion test passes
  **vacuously** — no draft exists, so nothing proves a draft would actually be excluded from a
  production build. That check is currently source-level assertion only.
- **Chromium only.** That is the only browser installed. No WebKit/Firefox, and no real iOS
  Safari — the 360px checks are emulated viewports, not a device.
- **No screen-reader testing.** axe-core is static analysis. It cannot tell you whether the ToC,
  the sources list or the meta `<dl>` actually *announce* sensibly in VoiceOver or NVDA.
- **External links unverified.** The link check is internal-only per the brief, so the post's
  9 outbound Microsoft Learn URLs were confirmed well-formed but never fetched. Whether they
  still resolve, and still say what the post claims, is the editor's check and remains open.
- **`site` is `http://localhost:4321`** per CONTRACTS §4, so every canonical, OG, RSS and
  sitemap URL is a localhost URL. Correct against the contract; nothing about production URL
  correctness is verified, and it cannot be until a real domain is set.
- **No visual regression baseline.** First run of this suite, so there is nothing to diff
  against. Layout is verified only by the overflow and landmark assertions.
- **Dark mode is emulated** via `prefers-color-scheme`, and there is no theme toggle to test.
- **Contrast figures in the `tokens.css` header comment were not independently recomputed.**
  axe verifies the rendered result and passes, which is the claim that matters.
